# マルチフレームのキャンバス(Figma 風)— 0.3.0

`enableMultiPageCanvas` を渡すと、全ページを 1 枚のキャンバスにフレームとして並べ、クリックしたページを編集できる。
1 ページずつの表示(従来)はそのまま残る。利用側はどちらを出すか選べる(両方の切替を用意した構成ラフ・提案書のテンプレートを参照)。

## 仕組み

- **編集エンジンは 1 つ**。生きているエディタ(`EditorCanvas`)は常に 1 つで、編集中のフレームの位置に置かれる。ページを移っても作り直さない(iframe の中身だけ差し替える)。
- **他のページは見るだけの紙面**(`PageFramePreview`)。`srcdoc` の iframe に `sandbox="allow-same-origin"` で描く。編集用の属性は付けず、script は外す(動かないのにコンソールへ「Blocked script execution」が 1 枚ごとに出るだけ)。画面から遠いものは描かない(webpage は高さの実測がレイアウトに要るので見えていなくても読む)。
- **同時に読む紙面は 4 枚まで**(`requestPreviewSlot` / `releasePreviewSlot`、編集中のページに近い順)。150 枚を一度に読むと接続枠と主スレッドを占め、編集中のページの切替が 1 秒近く待たされた(実測 82ms → 912ms。絞って 220ms 前後)。
- **紙面に足すスタイルは利用側が渡す**(`io.previewStyles` → `PreviewStyle[]`、URL か CSS 文字列)。本文が Tailwind のブラウザ版 JIT(script)に頼っている利用側(提案書)は、それが無いと紙面が素の HTML になる。提案書のテンプレートは自分のページの stylesheet と `/src/index.css`(dev)を渡す。構成ラフは本文に CSS が入っているので不要。
- **倍率は外側の CSS transform が持つ**。iframe の中は常に等倍(`generateEditableHtml(…, { embedded: true })`)。座標を親 ⇄ iframe で渡す箇所はすべて `iframeRect.width / iframe.clientWidth` の実測で倍率を掛ける(単独表示では 1 になるので同じ式でよい)。
- **iframe の中で起きたホイール・キー・中ボタンは親へ転送する**(`utils/embedded-canvas-bridge.ts` → `useInfiniteCanvas`)。座標は転送前に親の座標へ直す(親の realm で作ったリスナーから `postMessage` すると `e.source` が親自身になり、送り元の iframe を特定できないため)。
- **選択枠・ハンドル・コメントのピンは画面上で同じ太さ**。外側の倍率を `<html data-outer-zoom>` に書き、`applyOverlayScale` が内側 × 外側で割る。
- **フレームの寸法**: 幅は版面の幅(webpage は `artboardWidth`、slide は 1920)。高さは実測(生きているページはエディタ、他は見るだけの紙面の `#artboard` を `ResizeObserver` で)。位置は寸法から毎回計算する(状態に持たない)。
- **見えている範囲は記憶する**(`canvasStorageKey`、省略時は `parentId`)。開き直すと同じ場所に戻る。内容と重ならなければ編集中のページに合わせる。
- **倍率・位置は Context の外の小さなストア**(`viewStore`、`useCanvasViewState()` で購読)。ホイール 1 目盛りごとに Context の値を変えると、購読しているもの全部(エディタ本体・150 枚の紙面・左パネル)が描き直しになる。パンで変わる DOM は転写層とオーバーレイの transform の 2 つだけ(実測)。フレーム 1 枚ずつの要素は memo で倍率だけに依存する。
- **フレーム名は行の隙間に収まる倍率でだけ出す**。全体表示で 150 枚を並べると下の行の名前が上の行のフレームに被り、クリックを奪う(実測: 2 を押したのに 8 へ移った)。
- **キャンバスの余白から始めるマーキー**(`useCanvasMarquee`)。埋め込みでは iframe が紙面ぴったりで外側の「空白」が無いので、余白で押したドラッグを親が受け、矩形を iframe の座標に直して同じ判定(交差 → 最上位に畳む)で選ぶ。外→中に引くとページ全体の器の縁を必ずまたぐので、「他の候補をすべて含み、矩形にすっぽり入っていない」器は背景として外す。押している間はエディタの層を pointer-events: none にする(ポインタが iframe に入ると mouseup が親へ来ない)。

## ページ切替と保存

入口は 2 つ: フレームのクリック(フレーム名・左パネルのページ一覧も同じ)→ `activatePage(id)` → `onContentChange(id)`、
または利用側が `contentId` プロップを変える(構成ラフのレール、提案書の URL)。どちらも `FrontendVisualEditor.handleContentChange` に集まる。

1. `activatePage` はリング(選択枠)と名前の強調だけをクリックしたページへ移し(押した手応え)、生きているエディタはまだ動かさない
2. `handleContentChange` が **未保存の変更を先に保存**する(`flushAutoSave`。失敗したときだけ確認する。入口ごとに保存を書くと片方に漏れて 2 秒以内の編集が消える ── 実測で起きた)。断ったときは利用側の「編集中のページ」を今のページへ戻す
3. 本文を読む。順に `io.loadContent(id)` → `contentList[].thumbnailHtml` → `parentId` の API。連続して呼ばれたら最後の 1 つだけを通す
4. 読み込みから iframe の初期化が終わるまで自動保存を止める(`beginContentSwitch` / `endContentSwitch`)。止めないと、履歴に残っている前のページの本文を次のページへ書いてしまう
5. 本文が来た時点で `currentContentId` が変わり、エディタがそのフレームへ移る。新しい文書が描けるまで(`iframeReady`)エディタは隠し、下の見るだけの紙面が透ける(前のページの姿が新しい枠に見えない)。高さの報告先も `currentContentId`
6. 保存は常に `onSave(html, { auto, contentId })`。利用側は `contentId` で保存先を選ぶ。保存できた本文は見るだけの紙面にも写す(離れたあとも最新が見える)

## 利用側に要るもの

| 要るもの | 何のため |
|---|---|
| `contentList` | フレームの並びとタイトル。`id` は `contentId` と同じ体系 |
| `io.loadContent(id)` か `contentList[].thumbnailHtml` | 隣のページの本文 |
| `onSave(html, { contentId })` | どのページの本文かを見て保存する |
| `onContentChange(id)` | URL や「編集中のページ」を利用側が追う。逆に `contentId` プロップを変えるとエディタがそのページへ移る |
| `canvasStorageKey` | 見えている範囲の記憶(省略時は `parentId`) |
| `io.previewStyles` | 見るだけの紙面に足すスタイル。本文がブラウザ版 Tailwind に頼っている利用側だけ |

## 0.3.1 で足したもの(2026-09-13)

- **階層のツリー配置**: `contentList[].parentId` を渡すと、フレームをサイトマップの図と同じ姿(親の下に子を中央揃えで並べ、深さごとに行)で置く。親子は線でつなぐ(`TreeConnectors`、太さは `non-scaling-stroke` で画面上 1.5px)。階層が無ければ従来どおり行で折り返す(`layout: 'grid' | 'tree'`)。親が一覧に無い・循環しているものはルート扱い
- **別タブで開く**: `contentList[].href` を渡すと、フレーム名の右と左パネルの一覧に ↗ が付く(編集しない表示へ)
- **外から変わった本文の読み直し**: `contentList[].revision` を進めると、そのページの見るだけの紙面が `io.loadContent` で読み直す(編集中のページには効かない)。部品の定義を更新したとき(`updatePartFromElement` / 定義の編集)はエディタ自身が `invalidatePages({ except: [編集中] })` を呼ぶので、他ページの紙面がその場で変わる。紙面は次の本文が来るまで前の姿を出したまま(白く抜けない)
- **文書の属性** `documentAttributes`: `<html>` に付ける属性。生きているエディタと紙面の両方に、読み直さずに付け替える(`applyDocumentAttributes`)。構成ラフの「ノート(注釈カラム)の表示・非表示」に使う。値が null の属性は外す
- **紙面の iframe に sandbox を付けない**: script は本文から外している(`<script>` と onload 等のインラインハンドラ)。sandbox で script を禁じると、ページへ script を差し込むブラウザ拡張(React DevTools 等)が 1 枚ごとに「Blocked script execution in 'about:srcdoc'」をコンソールへ出す(実測 26 枚 = 26 件。ヘッドレスでは出ないので、拡張入りの Chromium で再現して確かめた)
- **縮小が軽くなった**: 紙面の iframe に `will-change: transform`。無いと倍率が変わるたびに 26 枚がラスタライズし直され、縮小中に 100〜340ms のフレームが混じる。付けると縮小 p95 117ms → 18ms、拡大 p95 167ms → 10ms(26 ページの構成ラフ、headless Chromium)。ぼやけは残らない(縮小 → 戻したあとの紙面を開き直したものと比べて画素差 0.0x%)
- **書体**: エディタの既定の書体をカスケードレイヤー(`@layer gg-editor-defaults`)に入れた。ページ側の CSS が `@layer base`(Tailwind v4)に書いた `html { font-family }` にも負けるので、本文が実際の見え方と同じ書体で組まれる(以前は `html, body` に直接書いていて、構成ラフだけシステム書体になっていた)
- **部品の見分け**: 部品(`data-part`)のルートを選ぶと選択枠・ハンドル・サイズラベルが紫になり、枠の上に「部品 <id> v<版>」の札が出る。中のスロットを選んでいるときは「部品の中 <id> v<版> › <スロット>」の札と、部品の外周の点線。右パネルの部品カードは中を選んでいても出て、「部品全体を選ぶ」「この姿で更新(全ページ)」「切り離す」が押せる
- **右のプロパティパネル**を Figma UI3 の寸法に寄せた(節は 1px の罫線、見出し 13px/600、入力 32px・角丸 6px・面の色、ラベル 11px)
- `EDITOR_VERSION` を公開。利用側が dev サーバーの束ねたコードと node_modules の版を見比べて「再起動してください」と出せる(構成ラフのテンプレートが実装)

## 0.4.0: 縮小のカクつきを直した(2026-09-13)

全ページが見えるところまで縮めると、ホイール 1 段ごとに主スレッドが 40〜50ms 使われていた。原因は 2 つで、どちらも直した。

### 1. ホイール 1 段の仕事を「合成だけ」にする

- **倍率・位置は React を通さない**。`MultiPageCanvasView` は `useCanvasViewState()` の購読をやめ、`viewStore.subscribe` から直接 style を書く。1 段で変わる DOM は **転写層とオーバーレイの `transform`、オーバーレイの `--ed-zoom` / `--ed-inv`、容器の `data-canvas-zoom`** だけ。編集中のページだけを購読する `useCanvasActivePageId()` を足した(倍率が変わっても描き直らない)
- **オーバーレイも転写層と同じ `translate + scale` の層にした**。フレーム名とリングは紙面の座標に置き、`transform: … scale(var(--ed-inv))` で倍率を打ち消す。画面上の大きさは今までどおりで、1 段あたりに React が触る要素は 0。名前は 1 枚ずつが小さな合成層(`will-change: transform`)なので、塗り直さずに動く。リングが出ているフレームだけは層にしない(フレームと同じ大きさの合成層を作らないため)
- **名前の出し分け・幅は「粗い倍率」から決める**(`coarseZoom`。150ms に 1 回まで、操作の終わりに必ず追いつく)。段ごとに変えると 26 枚の名前が毎段塗り直される

### 2. 転写層の中には「白い矩形 + 合成済みの iframe」しか置かない

フレームの枠線と階層の線を転写層の中に置くと、倍率が変わるたびに**転写層まるごと**が塗り直される。26 ページで 1 段 10〜20ms。`box-shadow` を `outline` や `border` に変えても、太さを粗い倍率で固定しても変わらない(塗り直しの原因は値の変化ではなく、縮尺が変わった層の記録し直しなので)。

そこで枠線と階層の線は転写層から出し、画面の座標の `<canvas>`(`CanvasFrameDecor`、`data-canvas-decor`)へ移した。26 本の矩形と 25 本の折れ線を 1600×1000 に描くだけなので 1ms もかからない(定規と同じ考え方)。canvas の寸法と色は、載せたときと容器の大きさ・テーマが変わったときだけ書く。

**階層の線の見え方が変わった(直した)**: 以前は `vector-effect="non-scaling-stroke"` に頼っていたが、Chrome の non-scaling-stroke は **祖先の CSS transform を打ち消さない**。実測で、画面上の太さは 100% で 1.5px、62% で 0.93px、25% で 0.37px、2% では 0.02px(見えない)。全体を見渡すために縮めたときほど線が消えていた。canvas では倍率に関係なく 1.5px で描く。

### 実測(構成ラフ 26 ページ、headless Chromium、DPR 2、CPU 4 倍遅く、⌘ホイール 30 段の縮小、3 回の中央値)

| | フレーム p50 | **フレーム p95** | 50ms 超 | 主スレッドの Paint |
|---|---|---|---|---|
| 0.3.1 | 8.7ms | **66.4ms** | 10 回 | 178 回 / 887ms |
| 0.4.0 | 8.6ms | **33.3ms** | 1 回 | 83 回 / 59ms |

提案書 150 枚(`verify-canvas.mjs deck-perf`)では、パン p95 9.2ms / ズーム p95 9.2ms、パン・ズームで style が変わる要素は 2 つのまま。

### 3. 大きく縮小したら紙面を画像にする(`contentList[].thumbnail`)

残った 33ms はほぼ 26 枚の iframe のラスタライズなので、利用側がページ全体を写した画像を渡せば iframe ごと外せるようにした。

- `contentList[].thumbnail` … ページ全体の PNG / JPEG の URL。幅 480px 以上、縦横比はページと同じ。内容が変わったら URL も変える(`&v=…`)
- 倍率が **0.5 未満**の間、そのページの紙面は `srcdoc` の iframe ではなく `<img>`(`object-fit: fill`)になる。本文は読まない(`ensurePageHtml` を呼ばない)。既に載っている iframe は外してメモリを返す
- **縮小の途中でも 0.4 を割った時点で画像に切り替わる**。切り替えるのは「画像が既に読めている」紙面だけで、やり方は容器の `data-canvas-preview-image="1"` を 1 つ立てるだけ(CSS が `[data-image-ready="1"]` の紙面の iframe を `visibility: hidden` にする)。26 枚がいっぺんに切り替わっても React は通らないので、1 段の仕事は属性 1 つの書き換えで済む。iframe を外して**メモリを返すのは操作が止まってから**(その間もラスタは止まっている)
- 画像がまだ読めていない紙面は iframe を見せ続ける(空白のフレームを出さない)。そのために、倍率 1.2 未満にいる間は画像を裏で先に読んでおく(`data-image-ready`)。1 ページを大きく開いて編集している間は読まない
- **iframe に戻す向きは操作が止まってから**(0.5 以上)。行き来でちらつかないよう、画像 → iframe は 0.5 以上、iframe → 画像は 0.4 未満(ヒステリシス)
- 画像にも iframe と同じ `will-change: transform` を付ける。無いと倍率が変わるたびに 26 枚の画像がラスタライズし直され、画像に落とした意味が薄れる(p95 で 8ms ほど違う)
- `thumbnail` が無いページ、画像が読めなかった(`onError`)ページは今までどおり iframe。編集中のページの生きているエディタは常に iframe
- 画像を出している紙面の `[data-page-preview]` には `data-preview-mode="image"`、iframe のときは `"iframe"` が付く
- 画像しか出していないページは iframe が高さを測れないので、画像の縦横比とフレームの幅から高さを出して並びに反映する

実測(構成ラフ 26 ページ + サムネイルを出す殻、DPR 2、CPU 4 倍遅く、62% で紙面が出揃った状態から ⌘ホイール 30 段の縮小、3 回の中央値):

| | p50 | **p95** | max | 50ms 超 |
|---|---|---|---|---|
| サムネイル無し | 8.5ms | 26.5ms | 94.8ms | 1 回 |
