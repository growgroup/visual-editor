# 依頼: @growgroup/visual-editor の UI/UX リデザイン

あなたは UI/UX とフロントエンド実装の両方に責任を持つリードデザイナー兼エンジニアです。
このリポジトリ(カレントディレクトリ、ブランチ `redesign/editor-ui-2026-09`)にあるビジュアルエディタの
**UI/UX を、より洗練されたものに設計し直し、実装まで行ってください。**

添付画像 2 枚は、利用側プロジェクト(Next.js の構成ラフ案件)で現行版を開いたときの画面です
(webpage モード、1920×1080)。左端の「構成ラフ / ページ一覧 / 共通パーツ」の縦レールと
「このページの編集を破棄する」は利用側(パッケージの外)が描いている部分で、それ以外の
上部バー・レイヤーパネル・キャンバス・下部フローティングツールバー・右パネル・フッターがこのパッケージの UI です。

## 1. このエディタは何か

- HTML をブラウザ上で直接編集する React コンポーネント(`src/index.ts` が公開 API)。iframe 内の DOM を直接操作する
- 2 つのモードがある(`editorMode`):
  - `slide` … 1920×1080 固定のスライド。提案書デッキの編集。発表者ノート・ページ並び替え・書き出しなど(`src/editor/components/ppt/PptChrome.tsx` がこのモードの外殻)
  - `webpage` … 可変高さの Web ページ。クライアント合意形成用の「注釈付き構成ラフ(ワイヤーフレーム)」の編集とレビュー。左に 1400px のワイヤー、右に 420px の注釈カラム、という 2 カラムの紙面を開く
- 保存先はエディタが知らない。`setEditorIO()` で利用側が渡した関数だけが外界との境界(README「設計」参照)。**渡されていない機能は UI ごと出さない**という規約がある(押すと失敗するボタンを残さないため)
- CSS は `npm run build` で `dist/editor.css` に作り切って同梱する。利用側の Tailwind バージョンに依存しない。preflight は含めない

利用側(読むだけ。**編集禁止**):

- slide モード: `/Users/user/orca/projects/temp/growgroup-proposal-react/src/editor-io.tsx`

## 2. 誰が、どういう場面で使うか

| 利用者 | 場面 | 主にすること |
|---|---|---|
| 制作会社のディレクター | クライアント打合せの前後、1920px または 1440px のノート PC | テキスト・並び・余白の修正、注釈の追記、コメントへの返信と解決 |
| クライアント担当者(非デザイナー) | 打合せ中に画面共有で、または後日 URL を開いて | 気になる箇所を選んでコメント、軽微な文言修正。ツールの学習コストをかけたくない |
| 制作チーム(デザイナー・実装者) | 修正ラウンド | 上記に加えてレイヤー操作、コンポーネント差し込み、CSS 変数、Figma 貼り付け |

UI の言語は日本語。文言は現行のトーン(簡潔・丁寧・専門用語を避ける)を保つ。

## 3. 「洗練された」の定義(この依頼で達成してほしいこと)

1. **情報階層の整理**: 常時見せるもの / 選択時に出すもの / メニューに畳むものを仕分ける。現行は左レイヤー・下ツールバー・右パネル・上部バーに機能が散っていて、初見の人がどこを見ればよいか分からない
2. **モードごとの最適化**: webpage モードは「レビューとコメントが主、編集が従」、slide モードは「編集が主」。同じ部品を使いながら、既定で見せるものと配置を変える
3. **一貫したデザイントークン**: 余白(4/8 の倍数)、タイポグラフィスケール、角丸、影・境界、ライト/ダーク配色(`PptTheme` が既にある。OS 設定追従)、フォーカスリング。パネル間で高さ・余白・文字サイズが揃っていること
4. **発見性**: コメントモードの入口、ショートカット(既存のものは変えない)、空状態(「要素を選択してください」等)、保存状態(未保存/保存済み/自動保存)の見せ方
5. **操作の手触り**: ホバー/選択のフィードバック、パネルのリサイズ、ズーム操作、トースト、ダイアログの一貫した振る舞い。過剰なアニメーションは付けない
6. **アクセシビリティ**: コントラスト(WCAG AA)、キーボード操作、Radix の ARIA を活かす。文字は 12px 未満にしない
7. **軽さ**: 体感のもたつきを増やさない。重いダイアログは遅延読み込みでよい

先に「何が問題か」を自分の目で確かめてから設計してください。添付画像だけでなくコードを読み、
必要なら後述の playground で実際に動かして確認すること。

## 4. 変えてはいけないもの(制約)

- **公開 API の後方互換**: `src/index.ts` の export、`FrontendVisualEditorProps`、`EditorIO` の契約。利用側 2 案件がコード変更なしでそのまま動くこと。新しい props やスロットを足すのはよいが、省略時は現行と同じ振る舞いにする
- 両モードが動くこと。webpage モードで絶対配置に倒さない(README「editorMode で挙動が変わる」)
- 保存・自動保存・書き戻しの意味論、`data-wf-*` 属性の扱い、コメントのデータ形式、`registerAutoSaveFlush` の挙動
- 「io に渡されていない機能は UI ごと出さない」規約
- 既存のキーボードショートカット
- CSS は `dist/editor.css` に作り切る方式(preflight なし)。利用側のページの見た目に影響する全体セレクタを足さない
- 依存の追加は最小限。Radix / lucide-react / cva / tailwind-merge / sonner は既にある。Web フォントの実行時取得は足さない(システムフォントで組む)
- 機能を削らない。整理して畳むのはよい
- **git**: 現在のブランチ `redesign/editor-ui-2026-09` に小さくコミットする(コミットメッセージは日本語、このリポジトリの慣例に合わせる)。`main` への切替・push・`npm version`・`npm publish` はしない(`main` に push すると GitHub Actions が npm に公開してしまう)
- このリポジトリの外は編集しない

**Phase 0 監査と設計** → `docs/redesign-2026-09.md` を書く:

- webpage モードと slide モードで何を変えるか
- 利用側に影響があるもの(あれば。原則ゼロ)

未着手の部分は docs に「未実施」と明記する。

**Phase 5 playground**: 動作確認のために `playground/` を追加してよい(Vite + React、devDependencies のみ。

ブラウザで確認できる環境なら実際に開いて確認し、できなければ docs に「未確認」と書く。

**最後に** `docs/redesign-2026-09.md` を更新して次を書く: 実施内容 / 未実施と理由 / 検証結果(typecheck・build・目視の有無) /
利用側での確認手順(`npm link` または `"@growgroup/visual-editor": "file:../../.claude/packages/gg-visual-editor"` で差し替えて
`npm run dev` → `/edit` を開く)。最終メッセージは日本語で、変更点の要約と未実施事項を簡潔に。

## 6. 作業環境について(重要)

- この依頼は**非対話**で実行される。質問はできない。判断に迷ったら自分で決め、根拠を docs に書いて進める
- **ネットワークは使えない**。`npm install` は失敗する。playground 用の `vite` と `@vitejs/plugin-react` は devDependencies に入れてある。
  他に依存が必要になっても足さず、無しで組むか docs に「必要な依存」として書く
- サンドボックスの都合で `git commit` が失敗する場合は、コミットせずに進めてよい(こちらで後からコミットする)。
  その場合も Phase の区切りごとに `docs/redesign-2026-09.md` の進捗欄を更新すること
- 依頼文の写しは `docs/redesign-2026-09-brief.md` にある
