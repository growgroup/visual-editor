# スライドを開くときの絶対配置への変換で版面がずれる(0.8.0 / 0.8.1)

利用者の報告: 提案書デッキをキャンバス表示にすると、見出しの下に置いたラベル(「追加」などの小さな帯)が見出しに重なる。

## 原因

スライドは開いた時点で、紙面の要素を**絶対配置へ倒す**(`convertToAbsolutePositioning`)。
インライン要素(`SPAN` など)は倒さず流れに残すが、変換後の自己検証は**倒した要素だけ**を前後で比べていた。

```html
<td>
  <div class="text-[26px] font-bold">見出し</div>
  <span class="mt-[10px] inline-block …">追加</span>
</td>
```

この形では、見出し(ブロック)だけが絶対配置で流れから抜け、残ったラベルが上へ詰まって見出しに重なる。
倒した要素は動いていないので、検証を素通りして変換が確定していた。

1 ページ表示では紙面が縮小されていて、端数で別の要素のずれが検出され**たまたま**巻き戻っていた。
キャンバスの編集中のフレームは等倍で採寸が正確なため変換が確定し、崩れた姿のまま編集が始まっていた。

## 直し

変換しないインライン要素の位置も前後で比べ、動いていれば既存の巻き戻しに乗せる(`src/editor/utils/dom-utils.ts`)。
巻き戻すと、そのスライドは絶対配置にならず流れのまま編集する(0.7.2 でも崩れなかったスライドの多くは、もともと巻き戻っている)。

## 確かめたこと

- 実物の `convertToAbsolutePositioning` / `makeChildrenEditable` を束ね、配信中の CSS を当てた headless Chrome で:
  - 提案書のスライド 160: 直す前は変換 44 要素・ラベルの重なり 61 / 26 / 26px(実際の編集画面の実測と一致)、直したあとは巻き戻されて重なりなし
  - 全 174 枚(等倍): 直す前 崩れなしで変換 152 / 崩れたまま変換 4 / 巻き戻し 18 → 直したあと 152 / 0 / 22。
    判定が変わったのは崩れていた 4 枚(012・160・161・173)だけ
- **実エディタ**(提案書デッキの複製に `npm pack` したものを入れ、キャンバス表示の編集中のフレームで採寸):
  - 崩れていた 3 枚(160・161・173)を一覧に足して比べた。**0.7.2 は重なり 4 / 4 / 3 件(26〜111px)、0.8.0 は 0 件**(巻き戻る)
  - もともと崩れていなかったページは変換の結果が同じ(ページ 100 は 93 要素を変換、23 は 39 要素、5・10・12・19 は巻き戻し)。
    直しすぎて変換が止まる回帰は出ていない

## 0.8.1: 編集対象でない罫線が上へ詰まる・全要素が 1px 膨らむ

0.8.0 のあとの報告: 縦積み(`#/all/5`)では正しいのに、編集画面に行くとヘッダーの罫線が上へ動き、版面がずれる。
iframe のせいではなく、同じ変換(`convertToAbsolutePositioning`)の 2 つの穴だった。

### 1. 編集対象でない、流れの中のブロックが上へ詰まる

- 部品(`data-part`)の中では `data-slot` だけが編集対象。ヘッダー部品のスロット(画像・小見出し・h1)は絶対配置へ倒されるが、
  スロットでない罫線(`<div class="mt-[22px] h-px w-full">`)は流れに残り、兄弟が抜けた分だけ上へ詰まる(実測 **116px**)。
  0.8.0 の自己検証は編集対象とインライン要素しか見ていなかったので、崩れたまま確定していた
- 直し: 編集対象の兄弟にある、編集対象でない流れの中のブロック要素も**一緒に倒す**(位置を固定するだけで、編集対象にはしない)。
  インラインのものは 0.8.0 と同じく動いたら巻き戻す

### 2. 全要素の幅・高さが 1px 膨らむ(`h-px` の罫線が 2px に)

- 寸法は縮小した紙面の `getBoundingClientRect` を倍率で割り戻して**切り上げ**ている(文字の折り返しを防ぐため)。
  ブラウザは矩形を 1/64px に丸めて返すので、56px × 0.55 = 30.8 が 30.8125 になり、割り戻すと 56.02 → 切り上げで 57。
  56px の帯が 57px、1px の罫線が 2px、カードが 249px(本来 248px)になっていた
- 直し: 丸めの分(1/64px ÷ 倍率 + 0.005)を引いてから切り上げる。端数の幅(1227.4px)は今までどおり切り上がる

### 確かめたこと(0.8.1)

実エディタ(デザインコンセプト資料 18 枚の複製に `npm pack` を入れ、1 枚表示・倍率 0.54)で、変換後の全要素の矩形を、
同じ文書で `data-gg-prestyle` を戻した(変換前の)矩形と比べた:

- 報告のスライド(5 枚目): 直す前は **41 / 59 要素**がずれ(罫線 −116px、幅 +1px が大半、罫線の高さ 1 → 2px)。
  直したあとは 5 要素・すべて 1px 未満(文字の幅の端数の切り上げ)。罫線も一緒に固定される(変換 47 → 48 要素)
- 18 枚すべて: **1.2px を超えるずれは 0**(残るのは 191.39 → 192 のような端数の切り上げだけ)
- 提案書デッキ(150 枚 + 崩れていた 3 枚): ラベル崩れの 3 枚は巻き戻り重なり 0 件のまま。もともと変換していたページは変換したまま
  (ページ 100: 93 → 95 要素、23: 39 → 41。増えた分は一緒に倒した編集対象でない兄弟)。リボンの枠線の検証 9 / 9

## 分かっている穴

- ドラッグ等のときに 1 要素だけを倒す経路(`convertSingleElementToAbsolute`)には、同じ検証を入れていない。
  その要素の兄弟(インライン・編集対象でないブロック)が詰まる余地は残っている
- 親の直下にある素のテキスト(要素で包まれていない文字)は倒せないので、兄弟が抜けると上へ詰まる。検証もしていない
- 幅の端数(191.39px など)は今までどおり切り上げるので、最大 1px 未満の差は残る
- 巻き戻したスライドは絶対配置にならないので、要素を自由な位置へ動かす操作は流れの中での移動になる(0.7.2 でも巻き戻っていたスライドと同じ)
