# キャンバスの操作の重さを測って直す — 2026-11

提案デッキ(1920×1080 のスライド 150 枚)をマルチフレームのキャンバスで開いたときの、パン・ズーム・ページ移動・
「1 枚」への切替・選択・文字編集の重さを測り、根拠の取れたものから直した。
**直したのは 4 ファイルと新しい 1 ファイル**(`contexts/MultiPageCanvasContext.tsx`・`hooks/useCanvasControls.ts`・`components/shell/PagesPanel.tsx`・
`components/ppt/PptChrome.tsx`、新規 `components/shell/useRowsNearViewport.ts`)。
`FrontendVisualEditor.tsx` は触っていない。

## 計測の仕方

- 環境: テスト用のデッキアプリ(150 枚)から `@growgroup/visual-editor` の src を直接読む。**本番ビルド**(`vite build` → `vite preview`)で測る。
  直す前のビルドと直した後のビルドを別のポートで同時に出し、交互に 3 回ずつ測って中央値を取った。
- スクリプトは 2 本(同じ操作・同じ出力の形)。
  - Orca 内蔵ブラウザ版: 実入力(agent-browser の mouse / press)。動作の確認と撮影はこちら。
  - ヘッドレス Chrome 版(Chrome for Testing・60Hz・1600×1000・DPR 2): **前後比較の数値はこちらを正とした**。
    当初は Orca のタブをアクティブにした計測を正にする予定だったが、Orca の描画の速さが窓の見え方で 120Hz〜1Hz まで変わり、
    前後で条件を揃えられなかった(下の「Orca の数値の読み方」)。
- 取るもの: Event Timing(INP 相当。16ms 以上の入力)、Long Animation Frame(scripts / render / style+layout の内訳つき)、
  rAF のフレーム間隔(p50 / p95 / max、25ms 超の数 = jank)、読み込み(FCP・LCP・TBT・編集できるまで)、Chrome のトレース。
- 操作の順: 読み込み → ⌘ ピンチ(ctrl 付き wheel を rAF ごとに 80 段)→ なめらかなパン(wheel を rAF ごとに 360 段)→
  左のサムネイルでページ移動(8 → 3 → 9 → 3)→ 全体表示(⇧1)→ 全体でパン → ⇧2 → 選択・ドラッグ・取り消し・文字編集 →「1 枚」。
  **編集は最後**(下の「計測スクリプトの直し」)。

### Orca の数値の読み方

Orca の **非アクティブなタブ** は、画面が変わり続けると描画が ~12fps(1 フレーム 66〜83ms)に絞られる。
対照実験: 50px の赤い div を `transform` で動かし続けるだけのページで、rAF の間隔は Orca(非アクティブ)p50 66ms、ヘッドレス 16.7ms。
アプリの処理が無くても 66ms になるので、これは Orca 側の絞り。

タブをアクティブにしても揃わない。同じタブ・`visibilityState=visible`・`hasFocus()=true` のまま、
ある回は p50 8.2ms(120Hz)、別の回は **1 フレーム 979ms(1Hz)**まで落ち、`orca eval` がタイムアウトした(01:29 からの回。Orca の窓が隠れていたためと見ている)。
このため Orca で取った INP・LoAF のうち「scripts 0ms・render 1ms なのに 80〜1000ms」のものは Orca の描画待ちで、アプリの処理時間ではない
(例: 選択クリックの処理そのものは 1〜17ms)。Orca は動作の確認(目視・機能のチェック)にだけ使い、数値の表には入れていない。

## 直したこと

### 1. パン・ズームの途中で紙面(iframe)を載せない — `MultiPageCanvasContext.tsx`

**再現**: ⇧2 で 1 ページを開いた状態から ⌘ ピンチで縮小 → 拡大、または大きくパンする。

**原因**: 画面に近づいた紙面は、その場で iframe を載せていた(同時 4 枚まで)。iframe を載せると本文の解析・スタイル・レイアウト・
初回のラスタが同じ主スレッドに乗る(srcdoc の iframe は同じプロセス)。縮小の途中は 1 段ごとに新しい紙面が画面に入るので、
その段のフレームに数枚分の仕事が積まれる。ヘッドレスのピンチ 80 段で、iframe は 21 → 67 枚に増え、フレーム 98 本のうち 22〜31 本が 25ms 超。
パン 360 段では 57〜67 本が 25ms 超(LoAF 50〜61ms、scripts はほぼ 0 = 描画側の仕事)。

**直し方**: 載せる枠(`requestPreviewSlot`)の配り方を変えた。
- 操作中(`markInteracting` から 160ms)は配らない。止まったら配り始める。
- 配るのは **主スレッドが空いたとき(`requestIdleCallback`、最長 200ms 待ち)に 1 枚ずつ**。以前は空きがあれば同じフレームで 4 枚配っていた。
- ページ移動の読み込み中(`activatePage` の間)も配らない。編集するページを先に出す。
  移動中かどうかは数で持つ(`activatingCountRef`)。移動が重なっても全部が終わるまで 0 に戻らず、数を上げるのは `try` の直前なので、
  途中で例外が出ても `finally` で必ず下がる(下がらないと紙面が二度と載らない)。サムネイルを 30〜60ms おきに 8 回押した後でも、
  最後に押したページ(7)が開き、全体表示で 150 枚が 5.5〜6.0 秒で載り切る(ヘッドレス 3 回)。

### 2. 「1 枚」の倍率を容器の大きさに合わせ続ける — `useCanvasControls.ts`

**再現**: 「1 枚」で開いた後に窓の大きさが変わる、または切替の直後に容器が組み上がっていない。Orca で 1002px 幅で開いて 1600px に広げると、
紙面が **19% のまま**(全体表示なら 50%)。以前の報告の「3%」も同じ経路(フィットの計算が 100ms 後の 1 回だけ)。

**原因**: フィット倍率は「マウントの 100ms 後に 1 回」と window の `resize` でしか計算しておらず、倍率に反映するのは最初の 1 回だけだった。
パネルの開閉・切替直後のレイアウトのように window が動かない容器の変化は拾えず、その時点の容器が小さければ豆粒のまま残る。

**直し方**: 容器を `ResizeObserver` で見て、フィット倍率を計算し直す。人がまだ倍率を動かしていないときだけ、
倍率もフィットに合わせ直す(PowerPoint の「スライドを画面に合わせる」と同じ)。幅か高さが 120px 未満の容器(組み上がる前)では計算しない。
- 「人が動かしたか」は `userZoomedRef` で別に持つ。ホイール・ピンチ・100%・選択範囲へのズームで true、全体表示(`zoomToFit`。⌘0・ヘッダー・「画面に合わせる」)で false。
  ヘッダーの倍率メニューや PowerPoint 風 UI のスライダーのように外から `setZoom` されたときも、このフックが自分で入れた倍率と違えば true にする。
  「いまの倍率がフィット値に近いか」で決めると、手でズームしてたまたまフィット値で止めたとき、次のリサイズで追従に戻ってしまう(レビューの指摘)。
- 追従するのはスライドだけ。webpage は本文の高さ(`canvasHeight`)が変わるたびにフィット値が変わるので、追従させると編集中に倍率が勝手に動く。
  webpage は最初の 1 回だけ合わせる(以前と同じ)。

確かめたこと(ヘッドレス・本番ビルド・「1 枚」): 1002px で開く 19% → 1600px 50% → 1200px 29%(追従)。ctrl+ホイールで 76% にした後は
1600px・1002px にしても 76% のまま。⌘0 で 19% に戻すと 1600px で 50%(追従に戻る)。1200px(フィット 29%)でヘッダーの「50%」を選び、
1600px(フィットも 50%)→ 1200px にしても 50% のまま(以前の判定ならここで 29% に戻っていた)。webpage は手元のデッキアプリに無いので確かめていない。

### 3. サムネイルの一覧は画面に近い行だけ紙面を描く — `PagesPanel.tsx`・`PptChrome.tsx`(PptThumbnails)・`useRowsNearViewport.ts`

**再現**: デッキを開く。または「1 枚」へ切り替える(エディタが作り直され、パネルも描き直される)。

**原因**: パネルは 150 行すべてで DeckSlideRender を描いていた。読み込み直後の DOM 13,124 のうち 10,224、img 554 枚すべてがこのパネル。
デッキアプリの io はこのために `/__slide/N` と `/__template/N` を 235 本取りに行き、表示するスライド 1 枚の取得
(`/api/presentations/.../slides/3`)がその後ろで 223 → 432ms 待たされていた。

**直し方**: 行は 150 本とも置いたまま、紙面(サムネイル)だけを画面に近い行で描く。Figma 風 UI の「ページ」パネル(PagesPanel)と
PowerPoint 風 UI のスライドのレール(PptThumbnails)で同じ仕組みを使う(`useRowsNearViewport`)。
- `IntersectionObserver`(root はパネル、`rootMargin: 150% 0px` = 上下 1.5 画面分の先読み)で近づいた行を覚え、**一度描いた行は残す**(戻ったときに白く抜けない)。
- 描いていない行も、同じ大きさの白い枠・番号・題名は出す。行の高さ(80px)と全体の高さ(12,030px)は変わらない。
- 見始めるのはレイアウトが落ち着いた 2 フレーム後。読み込み直後はパネルの高さが決まっておらず、すぐ見ると 150 行中 70〜79 行が「近い」と出た(2 フレーム後なら 26 行)。
- 編集中の行は最初から描く。`IntersectionObserver` が無い環境では全行描く(以前と同じ)。
- 描いたかどうかはページ番号でなく slide の id で覚える。並べ替えても、描いた行が白い枠に戻らない。

| なめらかなパン 360 段 | 25ms 超のフレーム / p95 / max / LoAF 最大 | 67 本 / 33.4 / 83 / 78ms | **0 本 / 16.8 / 16.8 / 0ms** |

各回の値(直す前 → 直した後): 「1 枚」[587, 581, 576] → [252, 266, 257]ms。編集できるまで [744, 755, 1120] → [414, 943, 422]ms。

### 全体でのパンの長いフレーム(83 → 117ms)は本当の悪化か

直す前・直した後(1〜3 の直し。スライドのレールの直しはキャンバス表示に関わらない)を交互に 5 回ずつ、同じ時刻に作ったビルドで測った。

| 条件 | 指標 | 直す前(各回) | 直した後(各回) | 中央値 |
|---|---|---|---|---|
| 150 枚が載った直後にパン | フレーム max | 67, 83, 33, 67, 83 | 100, 17, 117, 133, 133 | 67 → 117ms |
| 同上 | 25ms 超のフレーム | 3, 3, 3, 3, 3 | 3, 0, 1, 2, 1 | 3 → 1 本 |
| 載ってから 1.5 秒待ってパン | フレーム max | 117, 117, 50, 83, 50 | 150, 117, 50, 133, 100 | 83 → 117ms |
| 載ってから 5 秒待ってパン | フレーム max | 117, 67, 83, 50, 83 | 33, 117, 183, 100, 83 | 83 → 100ms |

| 150 枚が載った直後にパン(別の時間帯にもう 5 回) | フレーム max | 100, 133, 133, 83, 117 | 150, 133, 133, 83, 83 | 117 → 133ms |
| 同上 | 16.7ms を超えた分の合計(止まった時間の合計) | 202, 267, 234, 201, 217 | 167, 252, 184, 101, 68 | **217 → 167ms** |
| 同上 | 25ms 超のフレーム | 5, 8, 5, 7, 6 | 2, 3, 4, 3, 1 | **6 → 3 本** |

20 回ずつを合わせたフレーム max の中央値は 83 → 117ms。

**長いフレームの中身(Chrome のトレース。devtools.timeline・timeline.frame・blink・cc・gpu)**:
- 長いフレームは主スレッドの `ProxyMain::BeginMainFrame` 1 本(直す前 119ms・直した後 174ms)。その 93% が `LayerTreeHost::WaitForCommitCompletion`(111ms・161ms)で、
  主スレッドは何もせずに合成スレッドの commit を待っている。React・JS(FunctionCall 1.4ms)、style/layout(1ms)、Paint・Layerize(3〜4ms)はいつものフレームと同じ。
- 同じ時間に、ラスタ用のワーカーで画像の展開が積まれている(`GpuImageDecodeTaskImpl` → `Decode Image` → `DecodingImageGenerator::GetYUVAPlanes`。
  直す前 205ms・直した後 307ms)。パンで画面に入り直した紙面のタイルを描くには写真(JPEG)の展開が要り、それが終わるまで新しいタイルを出せず、commit が待たされる。
- パン 3 秒の間の画像の展開の合計は、直す前 681ms・直した後 851〜904ms(各 1〜2 回のトレース)。直す前後のどちらでも、パンのたびに同じ写真を展開し直している
  (2% で 151 枚・1 枚あたり数枚の写真が、展開の置き場に収まりきっていない)。
- **見立て(状態の切り替わりで React が 151 枚を描き直す、iframe の表示が切り替わって全面が描き直される)は当たっていなかった**。パンの始まり(`isInteracting` が切り替わるところ)のフレームは
  10ms 以下で、長いフレームは始まりではなく、始まってから約 2.3 秒(折り返しの後、紙面が画面に戻ってくるところ)に出る。

**試したこと(どれも戻した)**:
- 紙面の中の `<img>` を `decoding="async"` にする: 展開は 887ms に増え、max 150ms。変わらない。
- パン中に転写層・オーバーレイへ `will-change: transform` を付けない: 展開 1,075〜1,442ms、max 133〜150ms。悪くなった。

**結論**: 止まった時間の合計(217 → 167ms)と長いフレームの数(6 → 3 本)は直した後のほうが少ない。一方でいちばん長い 1 本は長くなった
(直す前は写真の展開がピンチ・パンの途中に散っていたものが、全体表示で戻ってくる紙面にまとまって来る)。
原因は写真の展開の量で、ラスタの段の仕事なので、載せる順番や React の状態では直らない。**直していない**。
直すなら、全体表示(紙面が数十 px)では写真を展開しない形にする。いまある「止まったら紙面を画像(サムネイル)に切り替える」仕組みがそれに当たるが、
デッキアプリが `page.thumbnail` を渡していないので働いていない。サムネイルを渡すのはホスト側の作業になる。

※1 直す前は、それまでのピンチ・パンの途中で 151 枚がすでに載り切っていた(そのせいで操作がカクついていた)。
直した後は操作中に載せないので、全体表示にした時点で約 90 枚、残りは止まってから 1 枚ずつ載る。


### 試して戻したもの

- **選択の React 側の描き直しを後ろへ回す**(`useEditorMessages.ts` の `ELEMENT_SELECTED` / `ELEMENT_DESELECTED` で
  `setSelectedElement` を `startTransition` で包む)。選択枠は送り手が iframe の DOM に直接描くので、React 側を遅らせても枠は同じフレームに出る。
  ヘッドレスで交互に 5 回ずつ測ると、選択クリックの INP は 40 → 40ms、選択解除は 32 → 32ms で変わらず、選択のフレーム max は 16.8 → 33.3ms
  (25ms 超が 0 → 1 本)と悪くなった。クリックの処理の中で `selectedElementIds` を先に更新していて(`useElementSelection.ts:639`)、
  これが急ぎの更新として同じ描き直し(右のパネルを含む)を起こすため、要素の更新だけ遅らせても INP は縮まない。
  パネルが 1 フレーム古い値を出すだけになるので戻した。縮めるなら、プロパティパネルを `selectedElementIds` でも描き直さない形
  (選択の文脈を分ける)にする必要がある。
  `EditorPropertyPanel.tsx` の中で `useDeferredValue` を使う案は効かない。パネルは `useEditorContext()` を直接読むので、
  文脈が変われば値を遅らせても全体が描き直される(区画は memo されていない)。

- **定規・枠線の canvas を CPU 描画にする**(`getContext('2d', { willReadFrequently: true })`)。Orca のトレースで、GPU の canvas が
  `CanvasRenderingContext2D::FinalizeFrame → GPU backpressure` で主スレッドを 29〜54ms 止めていたため。ただしヘッドレスでは同じ待ちが一度も出ず
  (Orca の描画の絞りが原因の可能性が高い)、A/B ではページ移動が 122 → 139ms、選択が 40 → 56ms と悪化した
  (容器の大きさの canvas を毎段 CPU で描いてテクスチャとして送り直すため)。戻した。

## 動作の確認(Orca 内蔵ブラウザ・本番ビルド)

- ページのパネル: 読み込み直後は 1〜30 行前後に紙面、その先は白い枠と番号・題名。パネルを 6,000px 下へ送ると 76〜85 行が描かれ、全体の高さは 12,030px のまま。
  `#/edit/120` へ移ると 120 の行まで自動でスクロールし、紙面も出る。
  ページの並べ替え(ドラッグ)と操作メニューは PagesPanel には無く、PowerPoint 風 UI のレール(PptThumbnails)にある。
- スライドのレール(PowerPoint 風 UI・「リボン表示」): 40 枚目で開くと 40 の行まで自動でスクロールし、紙面を描いた行は 150 行中 19 行(以前は 150 行)。
  全体の高さ 22,066px は描く前後で同じ。123〜128 行目まで送ると、見えている 6 行すべてに紙面が出る。
  行の「…」(`38枚目の操作`)でメニューが開き、上へ移動・下へ移動・複製・非表示・削除が並ぶ。
  並べ替え: 37 行目の dragstart で行が半透明になり、39 行目の dragover で差し込み線が出て、dragend で元に戻る
  (デッキの中身を変えないよう drop はしていない)。このレールに右クリックのメニューはもともと無い(「…」のメニューだけ)。

- キャンバス: 読み込み → ⇧1(2%、150 枚)で紙面が近い順に埋まる(0.6 秒で 90 枚、6.6 秒で 137 枚。Orca は描画が絞られているので遅め)。
  ⇧2 で 45%、サムネイルの 9 を押すと 9 へ移り、編集できる(`data-editor-ready`)。定規・フレーム名・リングは以前と同じ。
- ドラッグ: 144px 動かすと紙面で 318px(45%)動く。⌘Z で戻る。→ キーで 6px。文字編集(ダブルクリック 2 回)で文字が入る。
- コメント: ヘッダーの「コメント」でパネルが開く・閉じる。
- 「1 枚」: 50%(容器に合わせた全体表示)。1002px 幅で開いてから 1600px に広げると 19% → 50% に追従する(直す前は 19% のまま)。
  「キャンバス」へ戻ると元の倍率(45%)に戻る。
- 共同編集: 触ったのは紙面の読み込みの順番だけで、Hocuspocus の経路(`collab/`)には触れていない。デッキアプリに共同編集のサーバーが無いので実機の確認はしていない。

## 残った穴

- **「1 枚」への切替は 581 → 257ms まで。100ms 未満には届いていない**。残りはホスト側で、デッキアプリの `SlideEditor` が CanvasSlideEditor と
  SingleSlideEditor を丸ごと差し替えてエディタを作り直す(クリックの処理だけで 80〜100ms)。100ms 未満にするには、ホストが 1 つのエディタを保ったまま
  表示だけ切り替える必要がある。あわせて、キャンバスで 9 枚目を開いてから「1 枚」にすると 3 枚目が出る(デッキアプリが最初に開いた番号を使う)。
- サムネイルの一覧は、一度描いた行を外さない。端から端まで送ると 150 行すべてが描かれ、以前と同じ量になる。
- スライドのレール(PowerPoint 風 UI)の読み込みの速さは測っていない(計測スクリプトはキャンバス表示だけを通る)。描く行の数(150 → 19)だけ確かめた。
- `components/EditorCanvas.tsx` にも同じフィットの計算(100ms 後に 1 回・容器の大きさの確認なし)が残っている。いまは `useCanvasControls` が後から
  合わせ直して辻褄が合っている。1 か所にまとめたい(担当外なので触っていない)。
- **一度載せた紙面は外さない**。全体表示を一度でも通ると 150 枚の iframe がすべて残る(メモリ)。遠く離れた紙面を外す(骨組みに戻す)と軽くなるが、
  パンで戻ったときに一瞬骨組みが見える。どこまで離れたら外すかを決めてから入れる。
- 操作中は紙面を載せないので、**止まらずにパンし続けると、その間に画面に入った紙面は骨組みのまま**。止まって 160ms 後から 1 枚ずつ埋まる。
- 選択クリックの INP は 40〜56ms(中央値)。内訳は `handleMouseDown` が 10ms(強制レイアウトを含む)、その後の React の描き直し(右のプロパティパネル)が 20ms。
  `startTransition` で後ろへ回す案は効かなかった(上の「試して戻したもの」)。
  プロパティパネルの重い区画を memo で切り離す案も見送った。パネルの中身はほとんどが 1 つの部品(`EditorPropertyPanel`、3,268 行)の中に直接書かれていて、
  別の部品になっているのは 5 区画(GroupGeometry・InstanceOverride・ImgSrc・Link など)だけ。どれも選択している要素を受け取るので、memo しても選択のたびに描き直される。
  選択に関わらない重い区画を切り出せる形になっていない。
- Orca の非アクティブなタブでは描画が ~12fps に絞られ、アクティブでも窓が隠れると 1fps まで落ちる。フレームの滑らかさは Orca では確かめられない(ヘッドレスで確かめた)。
- 全体表示でのパン(2%、151 枚)のいちばん長いフレームが、直す前より長い(中央値 83 → 117ms。止まった時間の合計は 217 → 167ms と減った)。
  原因は写真の展開(上の「全体でのパンの長いフレーム」)。デッキアプリがサムネイルを渡せば、全体表示では画像に切り替わって展開が要らなくなる。
